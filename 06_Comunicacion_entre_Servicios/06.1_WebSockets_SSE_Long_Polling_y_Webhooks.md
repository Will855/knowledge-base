# 06.1 Comunicación en Tiempo Real: WebSockets, Server-Sent Events (SSE), Long Polling y Webhooks

> *"El modelo tradicional de petición-respuesta HTTP es unidireccional y reactivo; las aplicaciones modernas (chats, trading, tableros en vivo, gaming) requieren canales de comunicación persistentes y bidireccionales donde el servidor pueda empujar datos al cliente en tiempo real."*

## 2. Comparativa Técnica Exhaustiva

| Tecnología | Protocolo | Dirección | Sobrecarga de Cabeceras | Reconexión Automática | Firewall / Proxy Friendly | Casos de Uso Ideales |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Short Polling** | HTTP/1.1 | Cliente → Servidor | Muy alta (Headers completos en cada request). | Manual por código | Sí | Verificación de estados poco frecuentes. |
| **Long Polling** | HTTP/1.1 | Emula Servidor → Cliente | Alta (Reabre socket tras cada mensaje). | Manual por código | Sí | Fallback para clientes que no soportan WebSockets. |
| **Server-Sent Events (SSE)** | HTTP/1.1 / HTTP/2 (`text/event-stream`) | **Estrictamente Servidor → Cliente** | **Mínima** (Headers enviados 1 sola vez; luego streaming continuo). | **Nativa del navegador** (`EventSource`) | **Excelente** (Pasa por cualquier firewall/proxy estándar). | Feeds de cotizaciones de bolsa, resultados deportivos, notificaciones, outputs de IA (ChatGPT streaming). |
| **WebSockets** | Protocolo propio `ws://` (Upgrade desde HTTP) | **Bidireccional (Full-Duplex)** | **Cero** (Solo 2 a 10 bytes de framing por mensaje). | Manual (o con librerías como Socket.io) | Puede requerir configuración especial en Load Balancers L7. | Chats multiusuario, videojuegos multijugador, pizarras colaborativas (Figma). |
| **Webhooks** | HTTP POST estándar | **Servidor → Servidor** | Estándar HTTP POST | Reintentos configurados por el emisor | Sí | Integraciones B2B asíncronas (Stripe pagos, GitHub push alerts). |

## 3. Mecánica del Handshake de WebSocket

Un WebSocket comienza como una petición HTTP estándar y se "eleva" mediante la cabecera `Upgrade`:

```http
GET /chat HTTP/1.1
Host: api.petfhans.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

El servidor acepta y responde con **HTTP 101 Switching Protocols**:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

A partir de este instante, el protocolo HTTP desaparece y el socket TCP queda permanentemente abierto para intercambiar frames binarios o de texto bidireccionales con un overhead de solo **2 bytes**.

## Microtareas de Retención Intelectual

> [!QUESTION]- Active Recall: ¿Por qué SSE (Server-Sent Events) es superior a WebSockets para el streaming de respuestas de Inteligencia Artificial (ej. ChatGPT)?
> **Respuesta:** Porque la generación de texto de IA es un flujo **estrictamente unidireccional (Servidor → Cliente)**: el cliente envía el prompt una sola vez y solo necesita escuchar la ráfaga de tokens. SSE opera sobre **HTTP estándar**, lo que permite utilizar compresión nativa, multiplexación sobre HTTP/2, reconexión automática integrada en el navegador (`EventSource`) y compatibilidad total con firewalls corporativos y proxies sin el overhead de mantener canales bidireccionales de WebSocket.

---

> [!TIP]- Micro-Cálculo Mental: Overhead de Short Polling vs WebSockets
> **Reto:** Una app de chat tiene **100,000 usuarios activos**.
> - En **Short Polling**: Cada cliente hace un `GET /messages` cada 1 segundo con cabeceras de **800 bytes**.
> - En **WebSockets**: La conexión se abre una vez; los mensajes viajan con un framing de **2 bytes**.
> ¿Cuánto tráfico inútil de cabeceras genera el Short Polling por segundo?
> **Cálculo:**
> - Peticiones/segundo: $100,000 \text{ req/s}$.
> - Ancho de banda: $100,000 \times 800 \text{ bytes} = 80,000,000 \text{ B/s} = \mathbf{80 \text{ MB/s}} = \mathbf{640 \text{ Mbps}}$ de tráfico constante transmitiendo respuestas vacías.
> - *Lección:* WebSockets y SSE reducen el costo de infraestructura a una fracción minúscula.

---

> [!WARNING]- Dilema Arquitectónico: Seguridad en Webhooks Públicos
> **Escenario:** Tu plataforma recibe Webhooks de eventos de pago desde Stripe (`POST /webhooks/payment`).
> **Pregunta:** ¿Cómo garantizas que el atacante no falsifique peticiones enviando eventos de pago fraudulentos a tu endpoint público?
> **Respuesta:** Mediante **Firmas Criptográficas HMAC**. El proveedor (Stripe) firma el cuerpo de la petición con una clave secreta compartida y envía el hash en la cabecera `Stripe-Signature`. Tu servidor recalcula el HMAC-SHA256 del payload crudo y valida que coincida exactamente antes de procesar el pago. Además, se debe almacenar el `event_id` en una base de datos para garantizar **Idempotencia** ante reintentos duplicados.

---

> [!NOTE]- Desafío Feynman: Polling vs WebSockets vs Webhooks
> - **Short Polling:** Es como un niño en el asiento trasero preguntando cada 5 segundos *"¿Ya llegamos? ¿Ya llegamos? ¿Ya llegamos?"*.
> - **WebSockets:** Es como tener un intercomunicador de walkie-talkie abierto entre dos pilotos: cualquiera puede hablar en cualquier momento al instante.
> - **Webhook:** Es como dejar tu número de teléfono en el taller mecánico y decirles: *"No los voy a llamar; llámenme ustedes cuando el auto esté listo"*.
