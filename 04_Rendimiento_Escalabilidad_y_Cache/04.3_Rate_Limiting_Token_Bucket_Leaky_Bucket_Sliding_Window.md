# 04.3 Limitación de Tasa (Rate Limiting): Algoritmos, Redis Distribuido y Control de Tráfico

> *"El Rate Limiting es el mecanismo de defensa perimetral que protege a los servicios backend de abusos maliciosos (DDoS, scraping, ataques de fuerza bruta) y picos no intencionales de tráfico de clientes legítimos."*

## 2. Comparativa Técnica de Algoritmos

| Algoritmo | Mecánica Interna | Ventajas | Desventajas / Vulnerabilidades | Usado en |
| :--- | :--- | :--- | :--- | :--- |
| **Token Bucket** | Un cubo almacena tokens. Se añaden $r$ tokens/seg hasta capacidad $B$. Cada request gasta 1 token. | **Permite ráfagas cortas de tráfico (*Traffic Bursts*)**; memoria ultra-baja ($O(1)$). | Complejidad de ajuste de parámetros ($r, B$). | **Amazon Web Services (AWS API Gateway), Stripe**. |
| **Leaky Bucket** | Peticiones entran en una cola FIFO y salen procesadas a un ritmo constante y fijo. | **Suaviza el tráfico por completo (*Traffic Shaping*)**; salida predecible. | Las ráfagas legítimas se encolan o descartan aunque el backend tenga CPU libre. | **NGINX (`limit_req`), redes de telecomunicaciones**. |
| **Fixed Window Counter** | Cuenta peticiones en ventanas de tiempo fijas (ej. de 12:00 a 12:01). | Muy simple de implementar con `INCR` y `EXPIRE` en Redis. | **El Problema del Borde (*Boundary Attack*):** Permite el doble del límite en el cruce de ventanas (ej. 100 requests a las 12:00:59 y 100 a las 12:01:01). | APIs básicas con tolerancia a picos. |
| **Sliding Window Log** | Guarda el timestamp de cada petición en un *Sorted Set* (Redis ZSET) y elimina timestamps viejos ($t < \text{ahora} - \text{ventana}$). | **Precisión matemática absoluta del 100%**. | **Consumo de memoria colosal** ($O(N)$ almacena cada timestamp de cada request). | APIs de muy bajo volumen y alta seguridad. |
| **Sliding Window Counter** | Aproxima el tráfico combinando el contador actual con el ponderado de la ventana anterior: $\text{Req} = \text{Actual} + \text{Anterior} \times (1 - \text{progreso})$. | Memoria ultra-baja ($O(1)$) y elimina el problema del borde con $<0.05\%$ de error. | Es una aproximación estadística (no un log exacto). | **Cloudflare, Kong API Gateway**. |

## 3. Implementación Distribuida en Redis con Script Lua

En sistemas distribuidos con 20 instancias de API, los contadores deben ser atómicos para evitar condiciones de carrera (*Race Conditions*). Se usa un **Script Lua ejecutado atómicamente dentro de Redis**:

```lua
-- KEYS[1]: user_rate_limit:user_123
-- ARGV[1]: Capacidad máxima (ej. 100)
-- ARGV[2]: Ventana en segundos (ej. 60)

local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[2])
end

if current > tonumber(ARGV[1]) then
    return 0 -- Rechazado (HTTP 429)
else
    return 1 -- Aceptado (HTTP 200)
end
```

### Cabeceras HTTP Estándar de Rate Limiting:
```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1714567890
```

## Microtareas de Retención Intelectual

> [!QUESTION]- Active Recall: ¿Cómo vulnera un atacante un algoritmo de Fixed Window Counter para enviar el doble de peticiones permitidas?
> **Respuesta:** Si el límite es de 100 requests por minuto (ej. de 10:00 a 10:01), el atacante no envía nada hasta las **10:00:59** (donde envía 100 requests en 1 segundo), y a las **10:01:00** arranca la nueva ventana y envía otras 100 requests en 1 segundo. En un lapso real de 2 segundos, el servidor procesó **200 peticiones**, violando el límite de seguridad y pudiendo saturar la base de datos.

---

> [!TIP]- Micro-Cálculo Mental: Memoria de Sliding Window Log vs Counter
> **Reto:** Una API pública recibe **10,000 requests/segundo** por usuario. Ventana de 1 minuto (**600,000 requests en la ventana**).
> - Si usas **Sliding Window Log** guardando enteros de 64 bits (8 bytes por timestamp en Redis ZSET):
>   $600,000 \times 8 \text{ bytes} \approx \mathbf{4.8 \text{ MB de RAM por usuario}}$. Para 10,000 usuarios = **48 GB de RAM**.
> - Si usas **Sliding Window Counter** (2 enteros de 4 bytes):
>   $2 \times 4 \text{ bytes} = \mathbf{8 \text{ bytes por usuario}}$. Para 10,000 usuarios = **80 KB de RAM**.
> - *Ahorro:* 600,000 veces menos consumo de memoria.

---

> [!WARNING]- Dilema Arquitectónico: Rate Limiting por IP vs por API Key / User ID
> **Escenario:** Estás configurando el Rate Limiting para la app móvil de un evento en un estadio de fútbol (donde 50,000 usuarios comparten la misma antena 5G con una única IP pública vía CGNAT).
> **Pregunta:** ¿Qué ocurre si aplicas Rate Limiting por IP (`$remote_addr`)?
> **Respuesta:** **Bloquearás a los 50,000 usuarios legítimos.** Como todos comparten una sola IP pública por NAT, los primeros 5 usuarios consumirán el cupo y el resto recibirá error `HTTP 429`. **Solución:** Aplicar Rate Limiting basado en el identificador autenticado (`User ID` o `Bearer Token`), y reservar el filtrado por IP únicamente para endpoints públicos no autenticados (login/registro) con límites holgados o validación por Captcha.

---

> [!NOTE]- Desafío Feynman: Token Bucket
> Es como una máquina expendedora de tickets para un juego: la máquina suelta 1 ticket cada 5 segundos dentro de un tazón que puede guardar máximo 10 tickets. Si llegas corriendo puedes jugar 10 partidas seguidas de inmediato gastando el tazón (ráfaga); pero una vez vacío, estás obligado a esperar 5 segundos por cada partida nueva.
