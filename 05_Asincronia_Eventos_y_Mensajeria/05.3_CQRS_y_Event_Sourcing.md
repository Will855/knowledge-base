# 05.3 CQRS (Command Query Responsibility Segregation) y Event Sourcing

> *"En sistemas de alta escala, el modelo de datos óptimo para escribir transacciones rara vez es el modelo óptimo para consultar pantallas de usuario. CQRS divide la aplicación en dos caminos independientes: uno para mutar el estado y otro para leerlo."*

## 2. Event Sourcing: El Estado como Registro Histórico Inmutable

En bases de datos tradicionales (CRUD), un registro almacena únicamente el **estado actual**: `balance = 50`. Se desconoce cómo se llegó a ese número.

En **Event Sourcing**, la única fuente de verdad (*Source of Truth*) es un **Event Store append-only** que almacena cada hecho inmutable ocurrido en el tiempo:

```mermaid
graph LR
    E1["Evento 1: AccountCreated {id: 1, balance: 0}"]:::queue --> E2["Evento 2: MoneyDeposited {amount: 100}"]:::queue
    E2 --> E3["Evento 3: MoneyWithdrawn {amount: 30}"]:::queue
    E3 --> E4["Evento 4: MoneyWithdrawn {amount: 20}"]:::queue
    
    E4 --> Replay["Proceso de Replay / Plegado (Fold / Reduce)"]:::service
    Replay --> CurrentState["Estado Actual Calculado: Balance = USD 50"]:::service
```

### Snapshots (Instantáneas de Optimización):
Para evitar recalcular 1,000,000 de eventos históricos desde el principio de los tiempos cada vez que se carga una entidad:
* Cada $N$ eventos (ej. cada 1,000 eventos), el sistema toma una foto (*Snapshot*) del estado actual (`Snapshot en Evento 1000: Balance = USD 5000`).
* Para calcular el estado actual, carga el último Snapshot y solo aplica los eventos posteriores.

## 3. Matriz de Trade-offs de CQRS + Event Sourcing

| Ventajas | Desventajas / Complejidad |
| :--- | :--- |
| **Auditoría y Trazabilidad Total del 100%:** Cumple normativas bancarias y fiscales por diseño (nada se borra ni sobrescribe). | **Consistencia Eventual:** El lado de lectura tiene un retraso de milisegundos (*Projection Lag*). |
| **Escalabilidad Asimétrica:** Escala las lecturas (10,000 QPS en Elasticsearch) de forma independiente a las escrituras (100 QPS en Postgres). | **Evolución de Esquemas (*Schema Evolution*):** Modificar la estructura de eventos pasados inmutables requiere *Upcasters*. |
| **Viaje en el Tiempo (*Time Travel Debugging*):** Puedes reconstruir el estado exacto del sistema a cualquier segundo del pasado para reproducir un bug. | Curva de aprendizaje alta y sobreingeniería si se aplica a CRUDs simples. |

## Microtareas de Retención Intelectual

> [!QUESTION]- Active Recall: ¿Qué es el patrón Transactional Outbox y por qué es indispensable al usar CQRS con bases de datos relacionales?
> **Respuesta:** En CQRS, si actualizas la base de datos de escritura y luego intentas publicar un evento en Kafka, tu servidor puede caerse entre ambos pasos (la base de datos se guardó pero el evento nunca se emitió, rompiendo el lado de lectura).
> **El Patrón Outbox:** Guarda el cambio de negocio y el evento en la **misma base de datos dentro de una única transacción ACID local** (en una tabla `outbox_events`). Un proceso en segundo plano (o *Debezium CDC* leyendo el WAL) lee la tabla outbox y garantiza que el evento se publique en Kafka al menos una vez (*At-least-once delivery*).

---

> [!TIP]- Micro-Cálculo Mental: Aceleración de Queries con Read Models
> **Reto:** Una consulta compleja de dashboard ejecuta un `SELECT` con 7 `JOINs` y agrupaciones sobre una base de datos normalizada con **10,000,000 de filas**, tardando **1,800 ms** (1.8 segundos).
> Al aplicar CQRS, un proyector asíncrono precalcula la vista completa en un documento JSON en **Redis/MongoDB**.
> La consulta del dashboard ahora es un `GET dashboard:user_123` en memoria RAM ($0.5\text{ ms}$).
> ¿Cuál es el factor de aceleración (*Speedup*) logrado?
> **Cálculo:**
> - $\text{Speedup} = \frac{1800 \text{ ms}}{0.5 \text{ ms}} = \mathbf{3,600\text{x más rápido}}$.

---

> [!WARNING]- Dilema Arquitectónico: ¿Cuándo NO usar Event Sourcing?
> **Escenario:** Estás construyendo un sistema estándar de gestión de inventario para una biblioteca escolar con 500 usuarios.
> **Pregunta:** ¿Recomiendas implementar Event Sourcing?
> **Respuesta:** **No. Es una sobreingeniería masiva.** Event Sourcing introduce una complejidad operacional colosal (mantenimiento de snapshots, versionado de eventos, proyecciones desincronizadas, consistencia eventual). Debe reservarse para sistemas con requisitos regulatorios estrictos (banca, seguros, cadenas de suministro, registros de auditoría médica) o dominios con alta contención de reglas de negocio complejas.

---

> [!NOTE]- Desafío Feynman: Event Sourcing
> Es exactamente igual que el extracto bancario de tu cuenta: el banco no guarda en un post-it tu saldo final de "USD 500"; guarda cada depósito de "USD 100", cada retiro de "USD 20" y cada compra con tarjeta. Si tienes dudas de tu saldo, sumas y restas todas las líneas del extracto para verificar el resultado final.
